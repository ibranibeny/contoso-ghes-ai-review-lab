AI code review for GitHub Enterprise Server, inside your own network

GitHub Enterprise Server doesn't include Copilot code review. This lab shows how Contoso adds it anyway: every pull request is reviewed by a model in Microsoft Foundry, grounded in Contoso's own engineering standards through MCP servers, with no API keys and no public endpoints.

The gap

Why GHES needs its own AI reviewer

On GitHub.com you can request a review from Copilot. On GitHub Enterprise Server that option isn't there, and many GHES customers can't send source code to a SaaS reviewer anyway. The building blocks are all available, though: GitHub Actions on self-hosted runners, a private model deployment, and MCP servers for context.

Not available on GHES

Copilot code review on pull requests

Built into GitHub.com and GHE.com. GHES is not in the supported list, so PR review on GHES needs your own automation.

Works alongside GHES

Copilot in the IDE and Copilot CLI

Developers can use Copilot through an enterprise cloud account on code checked out from GHES; GHES 3.22 adds a Copilot CLI setup that can use your own model provider (technical preview).

Runs fully on GHES

This lab: Actions + Foundry + MCP

Your runners, your network, your model deployment. Deterministic workflow that posts a review and a required status check.

Pilot on GHES

GitHub Agentic Workflows (gh-aw)

Agentic workflow with a GHES compatibility mode, bring-your-own Azure OpenAI/Foundry key or Entra ID, safe outputs and MCP allow-lists. Validate against your GHES version first.

Architecture

Three regions, one private path

Indonesia Central plays the customer's data centre with the GHES appliance. Southeast Asia is the Azure landing zone with the runners, the MCP servers and the AI gateway. East US hosts Microsoft Foundry. A site-to-site IPsec VPN stands in for ExpressRoute.

Step 1

Open a pull request

A developer pushes a branch to GitHub Enterprise Server and opens a PR, exactly as today.

Step 2

A private runner picks up the job

GHES queues the AI review workflow. The Actions Runner Controller on a private AKS cluster receives it over the site-to-site VPN.

Step 3

The reviewer reads the diff

No checkout of the pull request. The job reads the changed lines through the GHES API with its short-lived job token.

Step 4

It gathers context through MCP

Two Model Context Protocol servers on a private VM: GitHub's MCP server (read-only, pointed at GHES) and Contoso's engineering standards.

Step 5

It asks the model, with no keys

The runner pod signs in to Microsoft Entra ID with workload identity and calls Azure API Management, the AI gateway.

Step 6

The gateway reaches Microsoft Foundry privately

API Management checks the token, applies a per-repository token budget, then calls Foundry over Private Link with its own managed identity.

Step 7

Review and status land on the PR

Comments on the exact changed lines, a summary with cited rules, and a required ai-review/foundry status. A human still approves.

Step 8

Everything is measured

Token use per repository, latency and errors flow to Log Analytics and Application Insights.

Demo

The code review, on a real pull request

A developer opened Add year-end discount codes on our GHES 3.22 appliance. Within a minute the reviewer, running on a private runner and grounded in Contoso's standards through MCP, posted its findings and failed the required check. Azure Well-Architected Framework

Design decisions by pillar

What the lab does today, and what we recommend before production. The lab takes a few deliberate shortcuts (a lab certificate authority, connection-string Actions storage, a Developer tier gateway) so it can be built in an afternoon; each one is called out. One shortcut did not survive: the tenant removed the appliance's internet-facing admin rule within minutes, so GHES is administered from a private workstation, exactly as we recommend for production.

PillarIn this labFor production
SecurityKeyless end to end: workload identity → Entra ID → API Management → managed identity → Foundry. Foundry local auth disabled; model, MCP and GHES reachable only on private IPs. Pull request code is never checked out or executed by the reviewer; the model gets read-only tools; output is schema-validated before anything is posted.Remove the GHES public IP and reach admins over ExpressRoute or Bastion; add Azure Firewall for egress; Defender for Cloud, Key Vault for every secret, private AKS API with authorized access.
ReliabilityZone-redundant gateway IPs; ARC scales runners from 0; the reviewer reports error instead of blocking silently; API Management circuit breaker on 429/5xx; a failed review never deletes or changes code.Active-active VPN or ExpressRoute; API Management Premium across zones with a second Foundry deployment as backend pool; GHES high-availability replica; runner pools in two zones.
Cost optimizationgpt-5.6-terra (balanced tier) instead of the flagship; token budget per repository with llm-token-limit; runners scale to zero; diff size limits; review only non-draft PRs.Provisioned throughput or Data Zone deployments when volume is steady; route only large or risky PRs to a bigger model; reserved instances for GHES and AKS nodes.
Operational excellenceEverything is code: Bicep for three regions, numbered scripts, the reviewer and its prompt versioned in Git, a pinned runner image built in ACR. Status checks and job summaries give an audit trail on every PR.Promote the reviewer through rings (pilot repos first), track precision and acceptance of suggestions, alert on review failures and token budget usage.
Performance efficiencyModel in East US behind a private endpoint in Southeast Asia keeps data on the Microsoft backbone; MCP servers sit next to the runners; tool calls and turns are capped so a review finishes in seconds to a few minutes.Pick the Foundry region closest to your data residency needs; scale ARC by queue depth; cache standards documents; use streaming for very large PRs.
