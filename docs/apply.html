Apply AI code review to your GitHub Enterprise Server

GHES doesn't include Copilot code review, but it has everything needed to run your own: GitHub Actions on your runners, rulesets, and an API the reviewer can read. This page is the path we recommend, from first conversation to every pull request reviewed.

The pattern

What happens on every pull request

  1. 1Developer opens a pull request on GHES
  2. 2GHES queues the AI review workflow
  3. 3A private runner picks it up with its managed identity
  4. 4The reviewer reads the diff, then asks MCP servers for context and rules
  5. 5The AI gateway checks the token and the budget
  6. 6Microsoft Foundry returns a structured review
  7. 7Comments, summary and a status land on the pull request
  8. 8A human approves and merges
Three design choices make this safe to adopt. The workflow is ordinary GitHub Actions on your own runners, so your existing controls apply. Every hop is keyless, from the runner to the model. And the reviewer only advises: it comments and reports a status, and a person still approves the merge.

Prerequisites

What you need in place

ComponentMinimumNotes
GitHub Enterprise ServerGitHub Actions enabled, with external blob storage. A recent release (we used 3.22.3).Rulesets with Require workflows to pass before merging let you enforce one central review workflow across an organisation.
Self-hosted runnersLinux runners that can reach GHES and Azure privately. We used Actions Runner Controller on private AKS.Virtual machine runners work too. Give them a managed identity; never store an API key on a runner.
Network pathExpressRoute or site-to-site VPN between the GHES network and the Azure landing zone; private DNS for GHES, the gateway and Foundry.Only outbound connections from runners. Nothing in Azure needs to call GHES except the MCP server, over the same private path.
Microsoft FoundryOne AI Services resource with a chat model deployment, local (key) authentication disabled, private endpoint.Choose the deployment type for your data residency: Standard (regional) or Data Zone keep processing in a geography; Global Standard does not.
AI gatewayAzure API Management on a private IP in front of Foundry.Validates the caller's Entra ID token, enforces a token budget per repository, emits token metrics, uses its own managed identity to call Foundry.
MCP serversGitHub's MCP server (read-only, GITHUB_HOST pointed at GHES) and a small server for your engineering standards.Run them next to the runners. They give the model context: other files in the repository, and the rules it must cite.
ObservabilityLog Analytics and Application Insights.Token use and latency per repository from the gateway; review outcomes from the job summaries and commit statuses.

Rollout

A four-phase plan

Most of the effort is not technical. It goes into agreeing the data path with security, and into tuning the reviewer until developers find its comments worth reading.

Phase 0 · 1 week

Decide

  • Pick 3–5 pilot repositories with active pull request traffic and owners who want to try it.
  • Agree the data path with security: which region and deployment type, what leaves the GHES network (diffs and file excerpts, never secrets), who can see the logs.
  • Choose success measures: time to first review, share of AI comments accepted, defects caught before merge, developer satisfaction.
Phase 1 · 1–2 weeks

Build the platform

  • Deploy Foundry, API Management, private endpoints and DNS with Bicep. The infra/ folder of this lab is a starting point.
  • Create the runner pool with a managed identity, and trust your internal CA in the runner image.
  • Run the two MCP servers and load your engineering standards (Markdown files with rule IDs) into the standards server.
Phase 2 · 2–4 weeks

Pilot in advisory mode

  • Add the workflow to the pilot repositories. The ai-review/foundry status is reported but not yet required.
  • Collect feedback on every comment (helpful, noise, wrong). Tune the reviewer instructions and the standards, not the model.
  • Watch tokens per review in the gateway metrics and set a per-repository budget.
Phase 3 · ongoing

Enforce and scale

  • Make ai-review/foundry a required status for critical and high findings. Keep one human approval.
  • Use an organisation ruleset to require the central review workflow on every repository that matches a pattern.
  • Review quality quarterly against a fixed set of pull requests before changing the model or the instructions.

Turn it on

Three things per organisation, one file per repository

1 · Variables

Where the gateway and MCP servers are

Organisation-level Actions variables, shared by every repository. No secrets: the identity comes from the runner.

2 · Workflow

The review job

One small workflow. Copy it into each repository, or keep one central copy and require it with an organisation ruleset.

3 · Rules

Required status and approval

Require ai-review/foundry and one human approval on main. Start in Evaluate mode to see the impact before you enforce.

Organisation variables
# Organisation variables (Settings > Secrets and variables > Actions > Variables). None of these is a secret.
AI_ENDPOINT        = https://apim-<name>.azure-api.net/openai/v1
MODEL_DEPLOYMENT   = gpt-review
MCP_GITHUB_URL     = http://10.40.4.10:8082/mcp
MCP_STANDARDS_URL  = http://10.40.4.10:8080/mcp
Workflow
# .github/workflows/ai-review.yml  (same file in every repository, or one central copy required by a ruleset)
name: AI review
on:
  pull_request_target:            # workflow definition comes from the base branch, not from the PR
    types: [opened, synchronize, reopened, ready_for_review]
permissions:
  contents: read
  pull-requests: write            # post the review
  statuses: write                 # ai-review/foundry commit status
jobs:
  review:
    if: ${{ !github.event.pull_request.draft }}
    runs-on: ai-review-runners    # your self-hosted runners with a managed identity
    timeout-minutes: 15
    steps:
      - name: Review with Microsoft Foundry + MCP
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}      # short-lived job token, nothing stored
          PR_NUMBER: ${{ github.event.pull_request.number }}
          AI_ENDPOINT: ${{ vars.AI_ENDPOINT }}            # API Management AI gateway, private IP
          MODEL_DEPLOYMENT: ${{ vars.MODEL_DEPLOYMENT }}
          MCP_GITHUB_URL: ${{ vars.MCP_GITHUB_URL }}
          MCP_STANDARDS_URL: ${{ vars.MCP_STANDARDS_URL }}
        run: /opt/reviewer/.venv/bin/python /opt/reviewer/review.py
At scale, use an organisation ruleset. On GHES 3.22 an organisation owner can create a branch ruleset that targets repositories by name pattern and adds Require workflows to pass before merging, pointing at the review workflow in a central repository. New repositories are covered the day they are created.

Make it yours

Tune the reviewer with your own standards

The model is the same for everyone. What makes the reviews useful is what it is told to check. Write your rules as short Markdown sections with an ID, a reason and a severity, and serve them through the standards MCP server. The reviewer is instructed to search them and cite the rule ID in every comment.

standards/secure-coding.md (excerpt)
### CSG-SQL-01 Parameterized queries only
Never build SQL text with string formatting, f-strings, `%` or `+` concatenation, even for "internal" values.
Use driver parameters: `cur.execute("SELECT ... WHERE customer = ?", (customer,))`.
Severity when violated: critical (SQL injection, OWASP A03).

Reviewer instructions

Tone, focus and severity policy live in runner/reviewer/instructions.md, versioned and reviewed like code.

Severity threshold

Only critical and high findings fail the status. Medium and low stay as advice so developers aren't blocked by style.

Diff and tool budgets

Caps on diff size, model turns and tool calls keep reviews fast and costs predictable.

Security review

Questions your security team will ask

RiskHow the design handles it
A pull request tries to talk the reviewer into approving (prompt injection)The diff and description are framed as untrusted data; tools are read-only; the answer must match a strict JSON schema; findings must point at changed lines; the reviewer can only comment, never merge. The demo PR contains exactly this attack.
A pull request changes the review workflow to leak tokenspull_request_target runs the workflow from the base branch. The job never checks out or executes pull request code; it reads the diff through the API.
Source code leaves the networkRunners, MCP servers, the gateway and Foundry are all on private IPs. Foundry has public network access disabled and is reached through a private endpoint.
Stolen or long-lived credentialsThere are none to steal: runner pods get Entra ID tokens through workload identity, API Management uses its managed identity, the GitHub token lives only for the job.
Runaway costAPI Management llm-token-limit per repository, diff size limits, a cap on model turns and tool calls, and runners that scale to zero.
Model data usePrompts and completions sent to Azure Direct Models in Foundry are not used to train foundation models and are not available to OpenAI or other customers.

FAQ

Common questions

Does our source code leave our network?

The changed lines, the pull request description and any file excerpts the model asks for through MCP are sent to your own Foundry deployment over a private endpoint. Nothing goes to a public endpoint, and nothing is stored by the reviewer. Pick a Foundry region and deployment type that match your residency rules.

Can the AI block a merge?

Only if you want it to. The reviewer sets a commit status; your branch rules decide whether it is required. We recommend advisory mode during the pilot, then requiring it only for critical and high findings, with a human approval on top.

Which languages does it support?

Any language the model reads well. The quality comes from your standards: write them as short rules with IDs and examples, and the reviewer will cite them.

How long does a review take?

Seconds to a few minutes, depending on the size of the diff and how many tool calls the model makes. Model turns and tool calls are capped so a review always ends.

What does it cost?

Mostly model tokens, plus the fixed cost of API Management, the runners and the MCP VM. Every review reports its own token count in the pull request, so you can multiply by your model's price and set budgets per repository in the gateway.

What if the model or the gateway is down?

The workflow reports an error status instead of failing silently, and the gateway retries on throttling. The code is never changed by the reviewer, so a failed review only means a human reviews without AI help.

Can we use a different model?

Yes. Change the deployment behind the gateway; the workflow does not change. Evaluate on a fixed set of past pull requests before you switch.
